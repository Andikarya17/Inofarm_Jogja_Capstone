# Master dan ledger v2 — FIN03 backend

Lanjutan FIN16/2 November2026: editor Android pengelola tersedia untuk semua resource di dokumen ini dan REFERENCES.md melalui Beranda→Kelola akun, budidaya dan acuan. Draft/journal terenkripsi per server+akun, explicit review online, retry envelope/ID/hash identik; password akun hanya memori dan perlu diketik ulang saat retry. Pending tidak diganti otomatis; conflict/epoch/scope perlu review. Kontrak mutation/backend tidak berubah. [Panduan FIN17](../../docs/migration/finance-20261029/FIN17_INSTALL_RUN.md), [evidence/batas FIN16](../../docs/migration/finance-20261029/FIN16_ACCEPTANCE.md).

Dependency FIN02 `0bb4ca4`, branch `codex/finance-cultivation-masters`. `openapi.json` membekukan envelope create/update dan close/reopen master. Semua menggunakan schema_version, sync_epoch, operation_id, entity_id, entity_type, action, base_version, payload. ID path harus sama dengan entity_id. Action create base_version null; koreksi menggunakan versi saat dibaca, active boolean dan reason wajib (kecuali musim memakai status close/reopen). Parent greenhouse/season tidak dapat dipindah melalui PATCH. List default50/max100, cursor UUID ascending; parent filter tidak memperluas scope.

Resource: greenhouses, seasons, planting-groups, varieties, units, materials, grades, expense-categories, assignments. Tipe envelope memakai nama tabel (`planting_groups`, `expense_categories`, `greenhouse_assignments`). Setiap master mempunyai GET list/detail, POST create, PATCH update, GET `{resource}/{id}/audit` (cursor audit integer, default50/max100). Tidak ada hard DELETE. Pekerja tidak bisa mengubah master atau membaca categories/assignments/users. GH inaktif tetap terbaca untuk histori, tetapi tidak menerima write baru selain reaktivasi GH oleh pengelola. Varietas inaktif boleh tetap direferensikan kelompok lama; referensi baru harus aktif. Dimensi unit/material immutable (`mass|volume|count`), tidak ada faktor konversi otomatis.

Musim: start_date/end_date kalender, end>=start; close/reopen POST `/seasons/{id}/close|reopen` memerlukan reason dan base_version. Musim closed menahan perubahan kelompok dan tanggal musim. Semai/pindah kelompok, pindah>=semai. Varietas dan musim harus berasal GH sama. Tidak auto-convert legacy.

Assignment: create payload greenhouse_id, user_id UUID publik akun operasional aktif, effective_from RFC3339 detik+offset, effective_until nullable; update effective_from/until/active/reason. Unik akun+GH, reaktivasi memakai versi yang ada. Tidak mencabut scope pengelola sendiri. Membuat GH secara eksplisit memberi assignment pengelola pencipta; membuat akun pada GH secara eksplisit memberi assignment akun itu. Keduanya atomic dengan receipt dan audit parent. Detail assignment server tidak mengekspos bigint internal.

Administrasi akun memakai GET `/users?greenhouse_id=...` dengan pagination. POST `/users` memakai entity type `users` dan payload greenhouse_id, name, email, role, password (minimal 12 karakter). PATCH `/users/{id}` memakai greenhouse_id, name, role, active dan reason, dengan email dan password opsional untuk kompatibilitas klien lama. Email dinormalisasi ke huruf kecil seperti saat login, harus unik, dan boleh sama dengan email akun itu sendiri. Email baru menggantikan email login lama dengan UUID akun tetap sama. Perubahan akun mencabut seluruh token akun tersebut. Pengelola tidak dapat menurunkan peran atau menonaktifkan dirinya. Perubahan ditolak bila akun mempunyai penugasan di luar cakupan pengelola. Password tidak masuk receipt, audit, atau feed. Ledger menyimpan hash request untuk idempotensi.

GET `/users?greenhouse_id=...&for_assignment=1` memberi kandidat aktif yang memiliki penugasan di cakupan pengelola, tanpa penugasan di luar cakupan atau di greenhouse tujuan. Untuk pekerja aktif yang belum punya penugasan sama sekali, POST `/users/assignment-candidate` menerima greenhouse_id tujuan dan email lengkap. Endpoint memerlukan pengelola dengan akses tujuan dan mengembalikan satu kecocokan persis dalam `data`, atau 404. Akun pengelola tanpa penugasan memperoleh akses awal dengan membuat greenhouse. Penugasan tetap dibuat melalui envelope `assignments`, dengan pemeriksaan ulang kewenangan dan keunikan di transaksi ledger.

`GET sync/status` mengembalikan schema_version dan UUID sync_epoch metadata yang dibuat migration; bukan default bisnis. Semua mutation berbagi lock metadata singleton lalu memeriksa hak terkini, epoch, hash receipt dan version; menyimpan mutation+audit+receipt+feed dalam satu transaction. Ini memprioritaskan integritas dan commit-order feed untuk usaha kecil; throughput tinggi belum dibuktikan. Receipt tidak dipurge otomatis. FIN05 menambahkan pull dan outbox Android; belum tersedia pada FIN03.

Migration baru membuat tabel master+ledger; FK restrict. Read-only test MySQL guard tetap. Migration/test belum dijalankan pada inofarm_local; menjalankan server v2 pada database pengguna memerlukan migrasi target terpisah, tidak dilakukan lewat suite.
