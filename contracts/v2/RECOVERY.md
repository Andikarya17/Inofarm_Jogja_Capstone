# FIN15 recovery v1 — core locally verified

Manual system-wide backup is a separate server-configured capability: current active manager **and** public UUID in FINANCE_RECOVERY_OPERATORS. Empty by default. GH assignment alone never permits all-system data access. The Android UI receives status/checksum/counts only; no database dump, credentials, key, filesystem paths or public backup URL. No scheduler, retention, RPO/RTO or production restore operator is invented (Q08).

GET recovery/policy, GET recovery/backups (bounded cursor), POST recovery/backups {request_id,reason}, GET recovery/backups/{id}, POST recovery/backups/{id}/validate {expected_manifest_hash}. Same actor/request/reason retries do not create another backup. Preflight validation is distinctly labelled and is not successful restore. Production apply has no HTTP endpoint.

Private package: finance-recovery-v1 canonical manifest + HMAC-SHA256 using server APP_KEY, streaming per-table JSONL (base64 raw non-null database values; null stays null), schema definitions/fingerprints, PK order/count/byte SHA/next auto increment, attachment blobs by content hash, explicit financial totals, source epoch/server UUID and migration fingerprint. No .env or key bundled. All MySQL base tables must be InnoDB with a PK. Capture uses repeatable-read and the finance commit-order lock; schema migrations/legacy writers require operational coordination. All referenced blobs, including cancelled attachment records, must exist and match size/SHA. Unreferenced staging files/caches/generated PDFs are not authoritative backup data. Root/path canonicalization rejects public or HTTP-served disk roots and traversal/symlink escape. Default storage/app/recovery-private-v2 lies outside the served local disk. Base64 encodes database bytes losslessly; it is not encryption. No APP_KEY/configuration secret is packaged; production key escrow/storage protection remains an operator decision. Package manifest tampering, missing/extra data files and schema incompatibility fail closed.

Restore apply exists only as `inofarm:restore-isolated`: effective APP_ENV=testing and MySQL schema inofarm_test, distinct server UUID, owned fresh datadir/nonce marker and private file root under a dedicated drill directory. Target must contain only trusted migration baseline (migrations + sync_state); never drop/reset a populated target. Migrate from trusted source first; package DDL is never executed. Import only validated known table/column names with parameter bindings. Failure quarantines the owned target, not a successful restore. Reconcile all table rows/checksums, schema/FKs, exact money totals, snapshot/source hashes and attachment bytes before activating a new epoch. Next auto increments preserved. Then revoke restored tokens/sessions, interrupt stale backup jobs, record verification/audit and new epoch; old cursors/operations reject. These deliberate post-verification differences are recorded. No production restore, drop, user-app clear or user database changes authorized by this contract.

POST sync/reconcile reviews original operation + expected current epoch, never mutates business data or replays it. Current actor/role/GH checked, including missing-receipt parent lookup; malformed references reject422. Exact historical receipt hash -> receipt_found; missing receipt -> manual_review, not proof of never accepted. Wrong payload hash/identity/epoch reject. Android retains old envelope/hash/raw edits; historical receipt acknowledgement is explicit and fenced to current epoch/session. Missing receipts stay held for manual source/version comparison; no auto re-ID/rebase/replay or queue purge. UI states explain holds and unresolved data loss risk.

Primary technical references: [MySQL8 consistent reads](https://dev.mysql.com/doc/refman/8.0/en/innodb-consistent-read.html), [PDO string fetches](https://www.php.net/manual/en/pdo.setattribute.php). Repeatable-read consistent reads share one transaction snapshot; string fetches retain database numeric text and preserve null. These are implementation mechanisms, not a claim that backup creation alone proves recovery.

On epoch change, previous local authority is archived and server-version/base/body pointers cleared before fresh pull. An unchanged accepted cached copy can be re-established by exact body comparison; a lower/different restored copy never overwrites local content. Pending/raw copies remain held. Explicit historical acknowledgement of an old accepted operation retains differing local content as LOCAL, with current server body kept separately, without enqueue. Missing receipts/parents require manual review and are not silently reissued. SQLite schema9 remains additive-history compatible.
