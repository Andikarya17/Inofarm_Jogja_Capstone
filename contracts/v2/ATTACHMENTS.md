# Private record attachments

Schema9 adds metadata for `activity_attachment`, `harvest_attachment` and `expense_attachment`. Each file has its own globally reserved entity UUID, version, operation receipt, audit and change-feed entry. The owner remains an accepted activity/harvest/expense UUID; upload does not update its physical version, financial allocation or harvest balance. Files are immutable; a manager can cancel with a reason. Cancellation retains metadata and private bytes for history. There is no automatic purge while Q06 remains open.

Q07 production size/count/types are **unset**, as explicitly answered by the user. `FINANCE_ATTACHMENT_MAX_BYTES`, `FINANCE_ATTACHMENT_MAX_FILES` and `FINANCE_ATTACHMENT_MIME_TYPES` must all be configured validly before a new upload can commit. Missing/invalid configuration returns409 `attachment_configuration_missing`; policy fields remain null/empty where unknown. JPEG/PNG/PDF and32MiB are technical compatibility ceilings, not approved production defaults. Fixture32768bytes/2files is test-only. Operators must align PHP upload/post limits and reverse-proxy body limits with the chosen policy and multipart overhead; no deployment configuration was changed.

`GET attachments/policy?owner_type=...&owner_id=...` returns configured/upload_allowed, nullable max_bytes/max_files, allowed_mime_types, supported_mime_types/max_supported_bytes, policy_hash, current owner_version and all reasons. The current actor must be authorized for the owner even to read this policy. A worker may upload only for their own operational record; other assigned workers may read operational files. Financial files require a manager assignment. Current account, assignment, parent and role are checked for every list/detail/download/audit/upload/replay/cancel. New writes also require an active owner and open season where applicable. Old accepted receipts remain confirmable after close or policy changes, subject to current read/role access and binary identity verification.

`POST attachments` uses multipart form data with exactly two parts: `operation` (JSON string, max16KiB) and `file` (binary). [Envelope schema](attachment-operation.schema.json) binds owner_type/id/version, original_name, actual MIME, byte count and SHA256; it contains no local URI, path, credentials or binary. `entity_type` must match the owner. Original name excludes control characters and path separators, max200 Unicode characters; extension must match detected PNG/JPEG/PDF. The transport filename and declared content type are not trusted. Server validates actual length/hash, finfo MIME and format signature on every upload including replay. This is not malware scanning or a complete PDF/image parser. Metadata and file identity mismatches return422; technical body ceiling returns413.

The owner version is explicitly reviewed at submission. A stale parent returns409 `parent_version_conflict` with current_version; a new reviewed operation is needed. Count is checked under the same sync metadata lock as metadata/audit/receipt/feed, so simultaneous uploads cannot exceed the configured active-file count. Count exceeded returns409 `attachment_limit_reached`. Configuration/count changes can permit retry of the same previously unaccepted operation without changing its UUID or bytes. Accepted replay returns the original receipt/status201, not a second row. Cancel uses `POST attachments/{id}/cancel`, action cancel, base_version and reason; it does not need multipart.

`GET attachments` is owner-scoped, UUID-cursor paginated, optionally filtered active/cancelled. `GET attachments/{id}` returns the immutable accepted metadata snapshot after current authorization; `GET attachments/{id}/audit` is paginated. Metadata has no public URL or internal path. `GET attachments/{id}/content` rechecks authorization and verifies stored size/hash before returning bytes with private/no-store, nosniff, a safe attachment disposition and restrictive CSP. Corrupt/missing content returns500 `attachment_integrity_failed`; it is never silently replaced. Original accepted receipt confirmation does not certify the current storage health.

`finance_private` is a dedicated local filesystem disk, serve=false, throw=true. Optional `FINANCE_PRIVATE_ROOT` is an absolute directory outside the server's published roots; default is storage/app/private/finance-v2. Blobs use server-derived SHA256 paths, streaming staging, checksum verification, fsync and atomic rename. No original filename becomes a storage path. Metadata/identity/audit/receipt/feed are one MySQL transaction; filesystem and SQL are not one transaction. A rollback after blob finalization can retain a private orphan, without an accessible metadata record; retry verifies and reuses those bytes. Backup/recovery must include this disk and checksums. No orphan cleanup or production restore was performed.

The backend increment requires the matching Android attachment implementation before operational-photo feeds are enabled. APKs before native attachment core do not understand the two new operational attachment feed kinds. The native core adds schema6 encrypted copies/bindings, operational-only worker read/write allowlists, foreground multipart queue and bounded encrypted downloads; [local storage contract](LOCAL_STORAGE.md) specifies crash/replay behavior. File selection/review/preview UI is the next increment. Upload policy is disabled by default; legacy v1 remains separate.
